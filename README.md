# BedrockMapper

A small, lightweight top-down web map for an **official Mojang Minecraft Bedrock Dedicated Server**
(BDS). It reads the real BDS world out of its LevelDB and will show online players as live markers.

Not a BlueMap clone: no 3D, no isometric view, no Minecraft textures. Just a clean top-down map with
procedural colours plus player markers.

## Status

- **Milestone 1 - read a real world: done.** Opens a BDS 1.26 world, decodes real chunk data and
  finds the highest visible block of every column.
- **Milestone 2 - render one chunk as an image: done.** Turns a real chunk into a top-down PNG with
  procedural colours and elevation shading.
- **Milestone 3 - browser map: done.** Serves cached 256x256 terrain tiles and a Leaflet page with
  pan, zoom and a live Minecraft X/Z readout.
- **Milestone 4 - live player locations: done.** A behaviour pack reports online players from BDS
  through the official Script API; the map shows them as markers that move, appear and disappear with
  the players.

Verified against a world generated by **Bedrock Dedicated Server 1.26.51.1** (branch `r/26_u5`):
939 chunks, 9612 subchunks, all in `SubChunkPrefix` format version 9.

## Requirements

- **Node.js >= 22.6** - the project runs TypeScript directly with Node's built-in type stripping, so
  there is no build step and no bundler.
- An **official Bedrock Dedicated Server** world directory (the folder containing `db/`, `level.dat`
  and `levelname.txt`). Java Edition worlds, Paper/Spigot/Fabric and PocketMine/Nukkit are not
  supported and never will be - the storage format is entirely different.
- Linux x64, Windows x64 or macOS arm64. The LevelDB dependency ships prebuilt binaries for those;
  other platforms build from source and need CMake and a C++ toolchain.

## Installation

```bash
npm install
cp .env.example .env
# then edit .env and point WORLD_PATH at your BDS world
```

`WORLD_PATH` is the world **directory**, not the `db/` folder inside it:

```
WORLD_PATH=/opt/bds/worlds/Bedrock level
```

## Rendering a chunk (milestone 2)

```bash
npm run render-chunk                                    # chunk 0,0
npm run render-chunk -- --chunk 30,10 --scale 24        # any generated chunk
npm run render-chunk -- --chunk 30,10 --no-shading
```

Options: `--world <path>`, `--dimension overworld`, `--chunk x,z`, `--scale <n>` (preview upscale,
default 16), `--out <dir>` (default `./output`), `--columns <n>` (debug lines to print, up to 256),
`--no-shading`.

## The browser map (milestone 3)

```bash
npm run dev        # same as npm start, but restarts on file changes
```

Then open <http://localhost:3000>. The page is a full-screen Leaflet map of the world with pan, zoom,
the block coordinates under the cursor and the visible extent. That is all - no dashboard, no login,
no controls beyond zoom.

The server has these routes:

| Route | Purpose |
| --- | --- |
| `GET /tiles/{dimension}/{zoom}/{x}/{y}.png` | One 256x256 terrain tile |
| `GET /api/map/info` | World name/version, chunk count, chunk/block/tile bounds, centre, tile geometry, player poll interval |
| `GET /api/players` | The latest player positions (see [milestone 4](#live-player-markers-milestone-4)) |
| `POST /api/players` | Where the BDS addon reports positions; needs the API key |
| `GET /` plus `/map.js`, `/style.css`, `/vendor/leaflet/*` | The page and its assets |

Leaflet is served from `node_modules`, so the map works with no internet access.

### Tiles

A tile is a fixed 16x16 block of chunks: 256x256 blocks, one pixel per block, so `zoom` 0 means
1 pixel = 1 block. The server renders only that one zoom level and the browser scales those tiles for
the other levels (`minNativeZoom`/`maxNativeZoom`), which keeps the tile pipeline simple and means a
zoom change never waits on the server. `image-rendering: pixelated` keeps the terrain crisp when
zoomed in. Requesting any other zoom from the server returns 404.

Tiles are composed by block coordinate rather than by pasting 256 chunk images together, so chunk
boundaries line up by construction - there is no seam-producing step to get wrong. A tile also loads
the chunks one step north and west of its edge, purely so elevation shading continues across chunk
and tile borders.

The `/api/map/info` bounds come from the chunks that actually have block data, and the page opens
fitted to those bounds, so nothing about the centre or extent is hardcoded.

### Rendering a range of chunks up front

Tiles are rendered on demand, but a range can be rendered ahead of time so the
first visitor never waits on a cold tile:

```bash
npm run render-map                                        # every chunk that has data
npm run render-map -- --chunk-x=-10..20 --chunk-z=-10..20  # a chunk range
npm run render-map -- --force                             # ignore the cache and redraw
```

The range is in **chunk** coordinates and is rounded out to whole tiles. A range starting with a minus
needs the `=` form, otherwise Node's argument parser treats it as another option.

```
Rendering overworld tiles
  chunk range:        X -10..20, Z -10..20
  tile range:         X -1..1, Y -1..1 (16x16 chunks each)

  tile   -1,  -1 rendered   4/256 chunks     507 B    39 ms
  tile    0,   0 rendered 232/256 chunks   19801 B   379 ms
  tile    1,   0 rendered 248/256 chunks   42520 B   413 ms

9 tiles in 1.1 s: 9 rendered, 0 already cached, 0 empty (not written)
decoded 637 chunks
```

### Caching

Two layers, because decoding a chunk is the expensive part:

1. **Chunk surfaces in memory.** Each chunk is decoded at most once (up to 8192 chunks, then FIFO
   eviction). Chunks the world does not store are known from the chunk list and never looked up.
2. **Finished tiles on disk**, under `MAP_CACHE/tiles/{dimension}/{zoom}/{x}/{y}.png`. A cached tile
   is served straight from disk without touching LevelDB. Tiles are written via a temporary file and
   renamed, so a concurrent request cannot read a half-written PNG, and identical concurrent requests
   share one render.

The tile directory records which world snapshot produced it. When the BDS world has changed since,
the tile cache is dropped on startup rather than serving stale terrain. Each response carries
`x-tile-source: rendered | cache | empty` for debugging.

Tiles with no block data at all are served as a single shared transparent PNG and never written to
disk, so panning across an unexplored world costs nothing.

### Missing chunks

A tile is drawn from whatever exists. Chunks absent from LevelDB, chunks stored without block data
and individual unresolved columns are all left fully transparent, showing the page background. This
is not a rare edge case: BDS does not persist every generated chunk, so real worlds have holes inside
their generated area.

### Surface selection

Per column, subchunks are walked from the top of the world downwards; within each subchunk, Y from 15
to 0. The first block whose palette name is not "invisible" wins, and the scan for that column stops.
Invisible means air plus the technical blocks that never form a surface (`barrier`,
`invisible_bedrock`, `light_block*`, `moving_block`, `structure_void`). Visibility is resolved once per
subchunk palette rather than per block, so a chunk costs one pass over the subchunks that exist.
Water counts as a surface, so oceans render as water rather than as the sea floor. Only layer 0 (the
terrain layer) is considered; layer 1 is the waterlogging overlay.

### Colours

Colours are procedural, hand-picked flat RGB values - no Minecraft textures are used. Lookup order is
the exact block name, then name rules (`*_leaves`, `*_log`, `deepslate*`, `*sandstone`, `*_ore`, ...),
then a deterministic FNV-1a hash of the name mapped to a fixed-saturation colour. An unrecognised block
from a future update therefore gets a stable colour instead of crashing the renderer, and the CLI marks
it `[hashed fallback]` so gaps in the palette are easy to spot.

### Elevation shading

Each column is compared with its neighbours to the north and west. The pixel is brightened when the
column sits above them and darkened when it sits below, by 6% per block of difference, clamped to
0.7x..1.3x. That is enough to read hills, cliffs and tree canopies; it is not a lighting model. Columns
with no visible block are left fully transparent. In a tile the neighbours come from the adjacent
chunks, so relief continues across chunk and tile borders; a chunk rendered on its own only sees the
neighbours it has inside itself.

### Coordinate mapping

North is up, +X is right, +Z is down - the usual Minecraft map orientation. Minecraft block
coordinates are the authoritative system; every other coordinate is derived from them.

| Step | Formula | Example |
| --- | --- | --- |
| world block X/Z -> chunk X/Z | `floor(X / 16)`, `floor(Z / 16)` | `-1, -16` -> chunk `-1, -1` |
| world block X/Z -> local X/Z | `X - chunkX * 16`, `Z - chunkZ * 16` | `-1, -16` -> local `15, 0` |
| local X/Z -> pixel X/Y | `pixelX = localX`, `pixelY = localZ` | local `15, 0` -> pixel `15, 0` |
| pixel X/Y -> RGBA offset | `(pixelY * width + pixelX) * 4` | pixel `15, 0` -> offset `60` |
| world block X/Z -> tile X/Y | `floor(X / 256)`, `floor(Z / 256)` | `-32, -48` -> tile `-1, -1` |
| world block X/Z -> pixel in tile | `X - tileX * 256`, `Z - tileY * 256` | `-32, -48` -> pixel `224, 208` |
| world block X/Z -> Leaflet LatLng | `lng = X`, `lat = Z` | `-32, -48` -> `LatLng(-48, -32)` |

The browser uses `L.CRS.Simple` with an identity transformation instead of its default `y = -lat`, so
one Leaflet unit at zoom 0 is one block and `lat` runs the same way as Z. Nothing is projected: there
is no latitude/longitude meaning beyond Leaflet needing a `LatLng` object, and no axis is flipped or
transposed anywhere between LevelDB and the screen.

Floor division is used everywhere, never JavaScript's truncating `/` or `%`: block X `-1` belongs to
chunk `-1` at local X `15`, not to chunk `0`, and to tile `-1` at tile pixel `255`. Round-trip tests
cover negative inputs at every step.

## Live player markers (milestone 4)

Player positions never come from the world files. They come from the running server:

```
BDS Script API -> POST /api/players -> map server (in memory) -> browser polls -> markers
```

The behaviour pack lives in `addons/bedrock-map-player-tracker`; [addons/README.md](addons/README.md)
covers installing it on your server. It collects every online player's name, id, X/Y/Z and dimension
every 60 ticks (about three seconds) and POSTs them with `@minecraft/server-net`.

### The player endpoints

`POST /api/players` needs the shared secret from `API_KEY`, as either
`Authorization: Bearer <API_KEY>` or `X-Api-Key: <API_KEY>`. It expects:

```json
{
  "players": [
    { "name": "Daniel", "id": "-4294967294", "x": 1234.5, "y": 68, "z": -543.2, "dimension": "overworld" }
  ]
}
```

Each update **replaces** the previous one; nothing is merged and nothing is stored on disk, so a
player who left is simply absent from the next report. Unknown fields are dropped, malformed bodies
get a 400 that names the offending field, and a bad or missing key gets a 401 without touching the
stored list. With `API_KEY` unset the endpoint refuses everything with a 503 rather than accepting
anonymous updates.

`GET /api/players` returns the latest state:

```json
{
  "players": [ ... ],
  "updatedAt": "2026-09-17T20:31:04.512Z",
  "stale": false,
  "ageMs": 240,
  "timeoutMs": 10000
}
```

Before the first update ever arrives, `updatedAt` is `null` and `players` is empty. Add
`?dimension=overworld` to get only the players of one dimension; without it every player is returned,
each with its own `dimension`.

### Stale data

If nothing arrives for `PLAYER_DATA_TIMEOUT` milliseconds (10 s by default) the list is treated as
unavailable: `stale` becomes true, `players` is empty and the map removes every marker and says
`player data unavailable`. The map never assumes the players it last heard about are still online. An
empty world is not the same thing: with BDS reporting nobody online the map says
`no players in the overworld`.

### Markers

The browser polls `GET /api/players` every `PLAYER_UPDATE_INTERVAL` milliseconds (3 s by default) and
reconciles the markers: a player who moved keeps their marker, a player who joined gets one, a player
who left loses theirs. Markers are keyed by the Script API's player id where available and by name
otherwise, so a marker survives even a name change. Positions use the same block-to-Leaflet mapping as
the terrain tiles, straight from `web/coords.js` - there is no second coordinate system.

Hovering a marker shows the player name; clicking one shows the name, X, Y, Z and dimension. Y does
not affect where the marker sits, it is only shown. Only players in the mapped dimension get a marker:
someone in the Nether or the End is still reported by the API, with their dimension, but does not
appear on the Overworld map.

### Testing without a server

`fake-players` posts made-up positions to a running map server, which is enough to check the browser
side on its own:

```bash
npm run fake-players                            # two players walking in circles
npm run fake-players -- --count 4 --nether 1    # four on the map, one excluded
npm run fake-players -- --empty --once          # nobody online
npm run fake-players -- --invalid-key --once    # expect HTTP 401
npm run fake-players -- --malformed --once      # expect HTTP 400
```

Stopping it (Ctrl-C) is how to watch the stale-data behaviour: the markers disappear about ten seconds
later.

## How the world reading works

1. **Snapshot.** The world's `db/` directory is copied into `MAP_CACHE` and the *copy* is opened.
   The copy is refreshed only when the source files change, so restarts are cheap.
2. **Keys.** Chunk records are keyed by `int32 LE chunk X`, `int32 LE chunk Z`, an optional
   `int32 LE dimension` (omitted for the Overworld), a one-byte record tag and - for
   `SubChunkPrefix` (`0x2F`) records - a **signed** one-byte subchunk index. `-4` is the lowest
   Overworld slice (Y = -64).
3. **Subchunks.** Each `SubChunkPrefix` value is a format byte, a layer count, the subchunk index and
   then one bit-packed block-index array plus a little-endian NBT palette per layer. Layer 0 is the
   terrain; layer 1, when present, is the waterlogging overlay. Blocks are packed in
   `x -> z -> y` order, Y varying fastest.
4. **Surface scan.** Subchunks are walked from the top of the world down and each of the 256 columns
   is resolved once, giving the highest visible block and its Y.

Block identity comes from the palette's namespaced block names (`minecraft:podzol`), so there is no
per-version numeric block registry to keep up to date. A block added in a future 1.26.x update simply
arrives as a new name instead of breaking the reader.

## Read-only guarantee

The map never writes to the Minecraft world.

This needs more than "don't call put()". The LevelDB build BDS uses does **not** hold an exclusive
lock, so a mapper *can* open the live `db/` directory - and doing so is destructive: opening a
LevelDB read/write replays the write-ahead log and may compact tables. Verified on BDS 1.26.51.1, a
single `open()` against a running server's world rewrote three `.ldb` table files, the `MANIFEST`
and `CURRENT` underneath the live server.

So the reader always copies `db/` into the cache directory first and opens the copy. An integration
test hashes the source database before and after a read to prove it is untouched.

You can snapshot a running server safely; a copy taken mid-write may have a torn tail on the
write-ahead log, which LevelDB recovers from on the copy. For a fully consistent snapshot, run
`save hold` / `save query` / `save resume` in the BDS console around the copy.

## Library research

The important requirement was current Bedrock compatibility, not popularity. What was checked:

| Candidate | Last release | Verdict |
| --- | --- | --- |
| [`@8crafter/leveldb-zlib`](https://www.npmjs.com/package/@8crafter/leveldb-zlib) | 2026-07 | **Used.** Maintained fork of `leveldb-zlib` bundling Mojang's LevelDB (zlib-raw compressed blocks, which stock LevelDB rejects). Prebuilds for linux-x64, win32-x64, darwin-arm64. |
| [`mcbe-leveldb`](https://www.npmjs.com/package/mcbe-leveldb) | 2026-09 | **Used** for record decoding. Handles `SubChunkPrefix` versions 0-9 including v9, plus `Data3D`. Decoded all 7626 subchunks of the test world with zero failures at ~0.08 ms each. |
| `leveldb-zlib` (upstream) | 2022-05 | Not used. Unmaintained, `cmake-js` 6 / `node-addon-api` 3 era; the fork above exists because of this. |
| `bedrock-provider` + `prismarine-chunk` | 2024-06 | Not used, though it does still work: it loaded chunks from the 1.26.51.1 world correctly when given a `bedrock_1.26.45` registry. Rejected because it maps blocks through a pinned per-version `minecraft-data` registry, which has to be updated for each new Bedrock release, and it pulls in a large dependency tree for a map that only needs block names. |
| A hand-written LevelDB/chunk parser | - | Not needed. The compressed-block LevelDB part genuinely requires native code, and `mcbe-leveldb` already covers the current chunk format. |

`Data3D` (`0x2B`) also stores a heightmap, which would be a shortcut for surface detection, but on a
real BDS 1.26.51.1 world every entry was the placeholder value 127, so the reader scans the block
data itself.

## Testing

```bash
npm test                                                  # unit tests only
TEST_WORLD_PATH="/opt/bds/worlds/Bedrock level" npm test   # + integration tests
npm run typecheck
```

The integration suite is skipped, not mocked, when no world is configured. It covers opening the
world, listing chunks, decoding subchunk block data and palettes, top-down subchunk ordering, highest
visible block detection, unknown chunks, snapshot reuse, and the read-only guarantee. The renderer
suite adds coordinate/pixel mapping, colour rules and the hash fallback, shading behaviour,
nearest-neighbour scaling and PNG round-trips, plus integration tests asserting that every pixel of a
real rendered chunk comes from the block the world reader decoded.

The tile suite covers block/chunk/tile conversions and their round trips over negative coordinates,
map bounds, rendering a tile out of 256 chunks, missing chunks and columns staying transparent, and
empty tiles. Chunk alignment is checked two ways: synthetic chunks whose blocks are named after their
own world coordinates would expose any transposition or one-block offset, and against a real world
every pixel of several chunks - including chunk `18,-1` and chunk `-1,10`, whose negative coordinates
were verified in earlier milestones - must equal what the milestone 2 chunk renderer produces for that
chunk. The server suite drives the real HTTP endpoints: the page and its assets, `/api/map/info`,
PNG tiles served from cache on a second request, negative tile coordinates in the URL, empty tiles,
unknown routes and path traversal.

The player suite covers validating and rejecting update payloads, replacing rather than merging the
list, the staleness timeout, dimension filtering, the marker key rules and the block-to-Leaflet
conversion the markers share with the tiles. On the HTTP side it drives `POST`/`GET /api/players`
including both accepted header forms, a missing/invalid key, a wrong scheme, malformed JSON,
oversized bodies, a server with no `API_KEY` configured, and a short-timeout server going stale.

Decoded blocks were additionally cross-checked against Minecraft itself: for 23 sampled columns
(including negative coordinates) the running server's `testforblock` confirmed both the block the
reader reported *and* that the block directly above it is air - 46 of 46 assertions matched.

### Generating a world to test against

With BDS running, ticking areas force real terrain generation without a client:


## Known limitations

- Overworld only. The Nether and the End are modelled in the dimension registry but not rendered, and
  players in them are reported by the API but not drawn.
- One rendered zoom level (1 pixel per block). Zooming out scales tiles in the browser instead of
  rendering downsampled tiles, so a very large world is heavy to view at low zoom.
- BDS does not always persist a generated chunk (chunk 0,0 of the test world stayed absent until
  something in it changed), so a chunk can be missing block data even inside a ticking area. Such
  chunks appear as transparent holes in the map.
- Subchunks in a pre-1.2.13 numeric-ID format are reported and skipped rather than guessed at.
  Modern BDS rewrites them on save, so this only affects very old converted worlds.
- The world is read at startup: new chunks appear only after a restart, which is also when a changed
  world clears the tile cache. A refresh endpoint comes with the live-updates work.
- Only one reader may hold a given snapshot open at a time.
- Player tracking needs the **Beta APIs** experiment on the world, because `@minecraft/server-net` and
  `@minecraft/server-admin` are still pre-release modules. It is dedicated-server only.
- Positions are as fresh as the reporting interval: a marker can be up to about three seconds (plus
  one browser poll) behind the player, and a disconnect clears the marker on the next report.
- Simulated players spawned by the GameTest framework are skipped, because a script may only read
  players whose type its own pack imports. Real players are unaffected.
